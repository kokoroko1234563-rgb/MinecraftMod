# Balance and scaling plan (not yet implemented)

Agreed direction after reviewing the build, with the review's adjustments folded in. **Do this
after the first human playtest (`PLAYTEST.md`)**, then update `docs/design.md` and `HANDOFF.md`.
All numbers are starting values to tune in playtesting.

## The problem: the cheapest number always wins

Recipes that need a certified numeral accept *any* numeral with that certificate:

- Prime Core accepts any certified prime, so 2 works.
- Circuit Board accepts any certified even, so 0 works.
- Perfect Core needs a proven Mersenne prime, and 3 = 2² − 1 qualifies.
- The Duplicator copies certificates (game test `duplicator_copies_certificates`), so one cheap
  certified numeral gives unlimited crafts.

So the prime path is not a progression: the smallest numbers satisfy every recipe.

## Work items, in order

### 1. Each number can be spent only once (Prime Core, Perfect Core)

- **Rule:** a numeral's value can be used as a recipe ingredient at most once per world, per
  ingredient kind (the property, its `also` list and `proven_only`). Separate kinds have separate
  pools, so spending 7 for "Prime" doesn't block it for another kind.
- Copies may exist and the Duplicator keeps copying certificates; only the first copy crafted
  counts. Euclid's theorem and the Infinite Prime Well then drive the hunt for new primes.
- **Storage:** a per-world spent record in `core/knowledge` (no Minecraft imports), saved with
  `MathState`; bump the save format version.
- **Check vs. record (important):** check in the ingredient/recipe `matches`. Record only when the
  result is actually taken. Never record in `RiskyShapedRecipe.assemble`, which also runs for the
  preview every time the grid changes.
  - The vanilla Crafter fires no crafted event: give it its own hook, or refuse spend-gated
    recipes in Crafters.
  - The preview shows no result for a spent numeral.
- **Feedback:** the numeral's tooltip says "already spent for: Prime". The Library block gets a
  "Spent numbers" tab showing the largest value spent per kind.
- **Circuit Boards are exempt at first.** Each board needs four evens, early numerals are unary,
  and the Duplicator charges by value, so unique evens would be grind, not discovery. Revisit
  after playtesting.

### 2. A reachable minimum for the Perfect Core

- Add an optional `min_bits` (or `min_value`) field to the `axiomatic:certified_numeral`
  ingredient, generated by `tools/gen_assets.py`.
- **Start with something trial division can reach in the binary age, e.g. p ≥ 13 (8191) or
  p ≥ 31.** The originally proposed p ≥ 127 (a 39-digit number) needs a proven Lucas–Lehmer test.
  The design's own open questions say that usually needs group reasoning, which the scope rule
  excludes. Raise the minimum only once a Lucas–Lehmer route exists in the game.

### 3. Machine speed: duration = steps ÷ steps-per-tick

- Goal: heavy jobs take real time on one machine, so players choose between **more machines**
  (resources) and **a better algorithm** (proving).
- **Implementation:** keep computing the result up front on the worker thread
  (`MachineBlockEntity.runAsync`). Set the job's duration to steps ÷ a configurable
  steps-per-tick (start at 1,000, in `AxiomaticConfig`). Don't make the evaluator resumable
  mid-computation, which would be a big refactor for the same visible effect.
- Energy already limits speed (about one unit per step, 10 per tick from a coal dynamo), so this
  only bites when energy is plentiful (FE interop, many dynamos). That is the case worth covering.
- **Optional:** upgraded machines with higher steps-per-tick, crafted from rarer cores.

### 4. Parallel range jobs (after playtesting has shown real costs)

- Same-kind machines on one cable network share a splittable job; the duration divides by the
  number of machines.
- **Start with the jobs that split cleanly:** Test Bench range mode, and Prime Forge / Prime Well
  candidate searches. Don't try to split arbitrary bounded searches inside formulas.
- A split job must give the same result as an unsplit one; a refutation found by any worker
  refutes the whole job.
- Sequential work (Lucas–Lehmer) doesn't split; this lesson only lands once Lucas–Lehmer exists
  (see item 2).
- A Job Coordinator block can come later.

### 5. Performance guard

Heavy computation runs on worker threads, not in the server tick. So cap the number of concurrent
async jobs, queueing them fairly, rather than imposing a global per-tick step budget.

### 6. Notebook: Assumption Chambers as working memory

This already works: one hypothesis per chamber, and even + even = even uses four. Add Notebook
text framing chambers as working memory: proving a lemma first frees chambers, which is a real
reason to break proofs up.

## Tests to add

**Game tests**

- `prime_core_refuses_spent_prime`: 7 crafts a Prime Core once; a copy of 7 is then refused,
  including through shift-click.
- `spent_pools_are_separate`: 7 spent for one kind does not block it (or 8) for another kind.
- `perfect_core_needs_minimum`: a Mersenne prime below the minimum is refused, and one above it
  is accepted.
- `step_limit_slows_big_jobs`: a large job takes about steps ÷ steps-per-tick ticks.
- `split_job_matches_single_machine`: two Test Benches on one network give the same result as one,
  in about half the ticks.

**Unit tests**

- The spent record survives save and load (`MathStateTest`).

## Open questions for playtesting

- Is 1,000 steps per tick the right base speed?
- Should larger primes give more Prime Cores (for example, scaling with bit length)? The review
  leans yes: it rewards pushing size beyond the uniqueness floor.
- Do Circuit Boards ever need spend-once or another limit?
- Which Perfect Core minimum feels right once players reach the binary age?
